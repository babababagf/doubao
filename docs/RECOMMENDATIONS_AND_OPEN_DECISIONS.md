# 建议与未决事项

> 版本：V0.8  
> 状态：需要逐项确认  
> 说明：本文件中的“推荐”不能自动替代用户决定，尤其涉及账号、费用、发布和数据删除时。

## 1. 已确认、不再重复讨论的方向

- 产品只做豆包GEO获客，不做通用GEO平台。
- 一个商户一个网站，不做城市分站。
- 普通商户网页客户端、EXE发布助手、总后台、贴牌/代理管理端是四个独立应用；企业公开网站是独立静态交付面。
- 前期本地开发，不直接部署服务器。
- 界面开发优先级固定为网页客户端 → EXE发布助手 → 总后台 → 代理功能 → 贴牌功能；代理功能依赖先建立最小贴牌租户底层。
- DeepSeek负责问题拓展和写作，豆包API负责问题查询和名称命中。
- V1 每个问题只生成一篇规范文章，由企业资料、企业信息库、关键词/问题词、行业方向和创作指令共同约束；网站、头条和抖音复用同一文章快照，不保留三渠道 AI 改写版本。
- 控制台账户概览展示期限、关键词、算力、写作篇数、文章、成功发布篇数和图片空间；效果区只保留问题总量、豆包收录数、电话曝光量、电话点击量。
- 企业网站首发三套模板。
- EXE 本地扫码并保存独立浏览器资料；经平台域名白名单过滤的可移植会话包（完整 Cookie 属性、LocalStorage、SessionStorage、IndexedDB）由平台托管 KMS 信封加密备份，供同一商户跨机恢复，任何后台角色不能查看明文。
- 采用TypeScript主技术栈：Vue、Electron、Playwright、NestJS、PostgreSQL、Redis。
- 网页客户端和贴牌/代理共用管理端显示贴牌系统昵称与 Logo；只有总后台能设置，贴牌、代理和商户只能继承。
- 域名按总后台、贴牌/代理管理端、普通商户网页客户端、企业内容站根域名四种用途保存；绑定、解绑和切换由总后台控制。
- 贴牌自行配置并支付大模型API，可选DeepSeek官方、火山方舟或受控自定义兼容接口；平台无默认密钥。
- 贴牌自行配置对象存储/CDN，直属商户、所属代理及代理商户统一继承；SaaS服务器仍由平台提供。
- 总后台按规定字段开贴牌，贴牌按规定字段开代理，贴牌/代理按统一字段开普通商户；账号和密码均为 6～12 位字母或数字。
- 可开用户数按普通商户席位逐级预留；AI 拓展成功词扣 1 点，AI 写作成功篇扣 30 点及 1 篇写作额度；发布不设篇数上限，只统计成功数。
- 豆包检测只允许贴牌对单个或全部所属商户发起，普通商户仅查看自身结果。
- 豆包检测不扣算力点数、不设次数或日/月商业限制，固定走所属贴牌豆包 API，第三方费用由贴牌承担。

## 2. 必须提前补齐的建议

### 2.1 把“管理后台”和“业务API”区分开

推荐：两个客户端 UI 可以先做，但必须先冻结 OpenAPI 和状态枚举；不能等总后台或租户管理端完成后才想接口。

原因：否则表单、分页、任务状态和错误处理会在接入真实API时重写。

### 2.2 公共企业网站必须是第四个独立交付面

推荐：企业公开网站由静态生成器负责，不复用网页客户端Vue页面。

原因：公开站点需要抓取、速度和低资源；网页客户端需要登录、交互和大型组件，两者目标相反。

### 2.3 V1一个商户只允许一个活动发布设备

已确认：一个商户可重新绑定设备，但同一时间只有一个EXE设备能领取发布任务；同一物理电脑上的单个 EXE 可以绑定多个商户，并为每个商户建立独立工作区、设备会话和浏览器资料。

原因：会话备份解决换机重复登录的主要痛点，但多台活动设备仍会带来任务抢占和重复发布；V1 继续由设备租约保证同一商户只有一个执行设备。

### 2.3.2 媒体会话采用平台托管密钥

已确认：平台服务器负责媒体可移植会话包的 KMS/信封加密与跨机恢复。EXE 上传经过头条/抖音域名白名单过滤的完整 Cookie 属性、相关 Origin 的 LocalStorage、SessionStorage 和 IndexedDB；不能只上传 `document.cookie`。不上传完整浏览器目录、缓存、历史记录、平台账号密码或二维码临时态。新电脑登录同一商户后自动尝试恢复并重新验证发布页，失败才要求扫码。

原因：代运营场景需要降低换机和故障迁移的重复登录成本。该方案意味着平台专用加解密服务在授权恢复时能够短暂取得会话明文，安全和合规责任高于端到端加密，因此必须使用 KMS、每备份随机数据密钥、认证加密、租户隔离、审计、撤销和轮换。第三方平台仍可能按设备/IP/风控使备份失效，不能承诺 100% 恢复。

### 2.3.1 EXE 登录采用启动门，不采用业务页常驻表单

已确认：首次启动或无有效会话时展示独立登录页；单商户会话直接进入工作区；多个商户会话才展示工作区选择和添加账号。账号密码框不出现在媒体账号、任务或日志页，现有顶部表单仅保留为开发联调临时入口。

原因：认证是进入应用的边界，不是媒体账号业务动作。常驻密码框既混淆商户登录与平台扫码，也增加误输入、肩窥和凭证残留风险。

### 2.4 默认全自动最终发布

已确认：网页端创建任务后，EXE 自动填写标题、正文和图片并自动点击最终发布，不要求逐篇人工确认。验证码、短信、设备确认、页面结构变化、未知弹窗和提交后结果不明仍必须暂停转人工。

原因：全自动是产品目标，但最终提交不可安全盲目重试，必须用任务租约、业务去重、页面后置条件和结果核验控制误发。

### 2.32 发布批次和每日数量

已确认：网页端从可发布文章库选择文章、平台、目标账号和发布数量创建批次；头条、抖音默认每日各 3 篇并可分别调高。去重支持“单平台去重”和“全平台去重”，默认单平台去重。多个账号用于轮询分配文章，不默认广播重复内容。同一商户内多个账号逐条串行，不同商户可以并行。

建议：没有明确运营时间段前只实现每日配额与计划时间，不写死 9 点、14 点、19 点等具体时刻；后续把执行窗口作为商户设置。

### 2.5 AI配置失败默认不静默回退

已确认：贴牌密钥失效时暂停并通知，不存在平台默认密钥，也不能使用其他贴牌密钥回退。

原因：任何回退都会造成平台成本失控、跨租户责任和账务争议。

### 2.6 V1不做在线支付

推荐：套餐、有效期和额度由管理后台人工开通，先验证产品闭环；支付、退款、发票和自动续费后置。

原因：支付会引入订单、对账、退款、税务和安全，明显偏离当前核心。

### 2.7 V1不做网站留言表单

推荐：首页和文章页只展示电话、微信、二维码和地址；电话曝光及点击已能衡量转化。

原因：留言表单会引入垃圾信息、隐私同意、通知和客户数据保护。如后期确有需求再加。

### 2.8 不在V1加入AI图片生成

推荐：图库只使用商户上传的真实图片，系统负责压缩、裁剪和封面排版。

原因：AI图片会增加费用、真实性、版权和人物/产品失真风险。

### 2.9 文章和企业资料必须版本化

推荐：每次发布保存不可变文章版本和企业资料版本引用。

原因：发生投诉、内容修改或平台发布差异时可以还原当时实际发送的内容。

### 2.10 豆包简称需要风险提示

推荐：继续按简单包含规则，但对过短、行业通用或高频简称显示“可能误命中”提示，不改变用户要求的计数逻辑。

原因：简称如“AI”“优选”可能在无关回答中出现，造成命中量虚高。

### 2.11 发布适配器不要把平台规则写死在业务层

推荐：头条、抖音分别维护标题长度、图片数量、等待条件和定位器；业务层只提供标准发布任务。

原因：平台规则变化时只修改适配器，避免影响内容、后台和另一个平台。

### 2.12 从第一版EXE就设计升级与版本兼容

推荐：EXE独立版本、最低API版本、更新清单、SHA256和回滚路径从骨架阶段建立，正式分发前增加Windows代码签名。

原因：平台页面变化会频繁要求更新，不提前设计会导致无法快速修复客户客户端。

### 2.13 建立固定算力点数台账，但不做现金余额

已确认：AI 拓展成功入库词按 1 点/个，AI 写作成功文章按 30 点/篇并同时扣 1 篇写作额度。采用预占、成功确认和失败退回流水；豆包调用仍记录用量，但是否扣点待确认。

原因：可以控制商户用量和排查异常，又不把算力点数伪装成贴牌第三方 API 现金余额。

### 2.14 删除采用回收站，不直接硬删除

推荐：企业资料、问题、文章和任务先软删除；已发布文章删除前提示网站和媒体影响。

原因：AI生成和发布结果有追溯价值，误删后应可恢复。

### 2.15 时间统一

推荐：数据库存UTC，界面默认按Asia/Shanghai显示；日志明确时区。

原因：本地客户端、香港/大陆服务器和平台时间可能不同，统一可避免任务计划与统计跨日错误。

### 2.16 网页客户端桌面优先但保持基础响应式

推荐：以1280～1920宽度为主；手机可查看数据、任务和文章，但长文编辑和批量生成主要在桌面完成。

原因：完全移动端适配编辑器和复杂表格会延长V1周期，而完全不适配手机又影响商户查看状态。

### 2.17 登录与管理安全

已确认：V1由上级创建账号，账号和密码均为 6～12 位字母或数字；密码不回显并使用强哈希保存。推荐总后台强制 MFA、登录失败限流和短时锁定，短信登录后置。

原因：产品指定的密码字符空间较小，必须依靠哈希、限流、锁定和总后台 MFA 降低撞库与暴力破解风险。

### 2.18 开源和参考代码使用边界

推荐：优先官方脚手架、SDK和成熟开源库；引入前检查维护状态、漏洞和许可证。参考商业系统只参考流程，不复制私有前端源码。

原因：避免版权、许可证、安全和不可维护依赖风险。

### 2.19 品牌配置只保留一个事实源

推荐：平台默认品牌一份、每个贴牌品牌一份，只有总后台可写；贴牌、代理和普通商户只保存归属关系，不复制系统昵称和 Logo 字段。品牌接口返回版本号并允许短时缓存。

原因：复制到每个代理和商户后，贴牌换 Logo 时容易出现部分页面未更新，也会增加数据库和缓存失效复杂度。

### 2.20 自定义域名必须按用途拆分并可回退

推荐：总后台访问域名、贴牌/代理管理端域名、普通商户网页客户端域名和企业内容站根域名按用途独立配置；总后台变更时先验证 DNS 和 HTTPS，成功后再原子切换，并保留上一条可用绑定。

原因：管理入口和大批商户内容站的风险范围不同。混成一个字段或直接覆盖，可能一次换绑同时导致后台和所有网站不可访问。

### 2.21 Logo 上传限制

推荐：V1 只接受经过服务端解码校验的 PNG、JPEG、WebP，生成固定尺寸版本；不直接展示用户上传的原始 SVG 或 HTML。无 Logo 时使用平台默认图形，浏览器图标可由 Logo 自动生成。

原因：能控制页面布局、缓存体积和恶意文件风险，也避免每个界面自行裁剪。

### 2.22 方舟联网回答不能等同豆包 App 官方收录

截至 2026-08-06，火山方舟官方文档以`doubao-seed-2-0-lite-260215`演示 Responses API，并提供 Web Search 联网工具；火山引擎豆包搜索产品页说明搜索内容包含头条/抖音同源内容库。这里表示“具备联网检索并可能召回字节生态公开内容”，不代表可以强制只搜今日头条/抖音，也不保证任意一篇作品一定被索引、召回或出现在豆包 App 的回答中。

已确认：V1 界面使用“豆包收录数”作为产品名称，但其统计逻辑仍是豆包 API 回答中的企业名称命中计数。详情必须注明模型版本、是否启用 Web Search、检测时间、回答文本和返回信源；不能宣传为“豆包 App 官方索引收录量”。开发前用真实头条/抖音测试内容完成一次最小验证。

### 2.23 豆包客户端与方舟联网检索的边界

结论：不能把豆包电脑客户端表述为固定整合“互联网、今日头条、抖音”三类来源。客户端的检索路由、召回库和排序并未由方舟 API 对外保证；方舟 Responses 的 `web_search` 仅承诺获取公开互联网实时信息，且本项目实测“西安 GEO 哪家好”确实产生联网调用，但返回来源为 `m.tech.china.com` 和方舟检索跳转域，没有 `toutiao.com` 或 `douyin.com`。

V1 实施：统一使用方舟 `Responses + web_search`，强制实际联网调用、正文与 HTTPS 来源同时存在；来源链接是唯一渠道判断依据。今日头条/抖音命中可以展示为来源事实，但不能作为必然召回、未命中判定或“豆包客户端一致性”的承诺。若后续获得方舟官方提供的站点限定能力，再作为独立策略接入并重新验收。

官方依据：[火山方舟工具调用](https://www.volcengine.com/docs/82379/1958524?lang=zh)、[火山引擎豆包搜索](https://www.volcengine.com/product/search-agent)。

### 2.23 API配置参考界面但不照搬平台数量

推荐：保留参考界面的“别名、平台、请求地址、API Key、模型、测试”结构，再增加用途、API协议和联网搜索能力。V1只预置DeepSeek官方、火山方舟、自定义OpenAI兼容接口，后续按真实需求增加适配器。

原因：一次接入智谱、通义、百度、混元、Kimi等所有平台会扩大测试面，也与当前DeepSeek写作、豆包检测定位冲突。

### 2.24 自定义接口必须防SSRF

推荐：预设平台锁定官方地址；自定义接口仅允许HTTPS，服务端拦截内网、回环、云元数据地址、危险DNS解析和重定向，并设置短超时和响应体上限。

原因：如果直接允许贴牌填写任意请求地址，后台服务器可能被用于探测内网或把API Key发送到恶意地址。

### 2.25 贴牌自备对象存储但平台继续提供服务器

已确认：平台提供SaaS服务器、数据库、队列和任务编排；贴牌提供大模型API、对象存储和CDN。贴牌直属商户及代理链下所有商户都通过平台后端使用最终所属贴牌资源，永久密钥不下发。

建议：V1先提供阿里云OSS预设，正式上传采用预签名URL或STS短时凭证。存储企业图库、文章图片和静态网站；业务数据库、日志、AI回答、Cookie与安装包不放入贴牌Bucket。

官方依据：[阿里云RAM安全最佳实践](https://help.aliyun.com/zh/ram/product-overview/best-practices-for-identity-and-access-control)、[OSS预签名上传](https://help.aliyun.com/zh/oss/user-guide/upload-files-using-presigned-urls)、[OSS自定义域名](https://help.aliyun.com/zh/oss/user-guide/access-buckets-via-custom-domain-names)。

### 2.26 截图中的阿里云密钥必须轮换

截图直接展示了完整AccessKey ID与Secret。若为真实凭证，应立即禁用并轮换；系统实现不能回显Secret。建议使用RAM子账号或角色，并将权限限制到指定Bucket和对象前缀。

### 2.27 共用入口不等于前端菜单鉴权

已确认：贴牌和代理共用`tenant-admin-web`、域名和登录页；普通商户网页客户端及总后台各自独立。登录后菜单来自服务端角色权限，但每个接口仍需校验角色、租户和数据归属。

原因：只隐藏菜单时，代理仍可能通过直接 URL 或接口调用取得贴牌能力；同时把三个网页应用会话混用会扩大高权限账号风险。

### 2.28 分级开户采用席位预留

推荐：贴牌可开用户数覆盖直属和全部代理商户；分给代理时先预留。到期或停用不自动返还，明确关闭后才返还并记录审计。

原因：若贴牌和代理分别只检查自身当前账号数，同一批用户席位会被重复分配，最终超过总后台给贴牌的上限。

### 2.29 豆包全部查询必须有费用保险丝

已确认：只有贴牌可以选择单个或全部商户发起豆包检测。全部查询提交前展示商户数、问题词数和预计调用次数，并执行二次确认、分片、安全并发、提供方限流退避、幂等和失败续跑；不设置次数或日/月商业限制。

原因：全部查询可能瞬间产生大量由贴牌密钥承担的请求；没有预览和限额会造成费用失控，也可能触发提供方限流。

### 2.30 代理界面优先不改变租户依赖

已确认：管理应用界面按总后台 → 代理功能 → 贴牌功能开发，但后端阶段先建立最小贴牌租户、资源归属和额度账本，再允许代理存在。

原因：代理必须继承贴牌品牌、API、OSS和域名，没有上级贴牌实体时无法安全实现或测试。

### 2.31 写作篇数与发布篇数分开

已确认：写作篇数是可扣减额度，AI 成功生成一篇扣 1；发布不设篇数额度，普通商户看到的是按渠道成功结果累计的发布篇数。同一文章分别成功发到头条和抖音计 2 条。

原因：写作发生在云端 AI 任务，发布发生在两个媒体渠道；混为一个额度会导致多平台发布和失败重试无法对账。

## 4. 建议的简单额度模型

V1 采用以下简单额度模型：

- 贴牌可开代理数。
- 贴牌及代理可开普通商户席位，向下分配时预留。
- 商户关键词数量上限。
- 算力点数：AI 拓展成功词 1 点/个，AI 写作成功文章 30 点/篇。
- 写作篇数：成功生成文章 1 篇扣 1。
- 账号有效期。

发布不设篇数额度，只统计成功渠道结果；网站数量固定为每商户一个；电话数据不扣额度。失败、重复、取消和未入库的 AI 结果不扣或退回预占。豆包检测不扣点、不设商业次数限制，固定走所属贴牌 API；技术层只保留安全并发、提供方限流退避和幂等保护。

## 8. AI 创作任务并发处理建议

- 本轮不新增产品决策项。停止与 Worker 结算属于数据正确性约束，固定采用数据库条件更新、行锁和串行化事务，不交给前端状态判断。
- 不建议把控制台“可用算力”改成临时扣除预占后的数字；当前预占只影响能否创建新任务，成功后才计入实际消耗。若以后要展示，应新增“已预占”字段，不能偷偷改变现有指标口径。
- `P2034` 只做小次数有限重试并记录请求 ID；若生产频繁出现，应检查 Worker 并发、长事务和数据库负载，不能简单提高到无界重试。

## 9. 图片空间指标建议

- V1 只展示“贴牌存储是否可用”和“当前商户已用字节”，不展示剩余空间。贴牌 OSS 的 Bucket 容量通常没有可可靠分摊到商户的套餐上限，伪造总量会误导用户。
- 如果后续需要按商户销售存储额度，应新增独立的 `imageStorageLimitBytes` 权益和超限校验，再显示“已用/上限”；不能从 OSS Bucket 总容量倒推，也不能复用当前布尔 `available`。

## 10. 发布异常恢复建议

- 可恢复白名单建议保持小而固定：登录失效、提交前验证码、页面适配修复、填写校验修复。新增原因默认不可恢复，只有在能证明未触发最终提交后才纳入。
- 不为“结果不明”提供一键重试或后台强制解锁。现已实现独立的“人工核验已成功”：要求同平台官方作品链接并写审计，不复用续发接口；“确认未发布”仍未实现，因为缺少可靠的否定证据，不能据此直接重发。
- 不建议让资产缺失和内容无效原任务续发。这两类问题修正后会形成新文章版本，应新建任务才能保持版本、配图和审计一致。
- 会话备份状态可以向商户回显，但建议永远只显示“有/无 + 最后备份时间”。密文大小、来源设备、Cookie 数量等运维摘要也不应暴露给普通商户。

## 11. 计划任务调度建议

- 当前本地阶段建议继续使用“EXE 轮询触发 + 数据库条件更新”，不要为计划任务单独增加常驻进程。这符合前期简洁、低资源的要求。
- 上服务器后，如果出现无 EXE 在线但管理端仍需准确显示“已到期排队”，可增加一个低频全局激活 Worker。该 Worker 只能转状态，不能领取或发布。
- 时间字段长期建议迁移为明确 UTC/timestamptz 口径。当前不建议在未审计全部时间字段前单独修改 `scheduledAt` 列类型，否则可能改变历史任务实际时间。

## 12. 失败后修订文章与去重约束（已按 V1 文章级永久去重落地）

- 已确认 V1：数据库唯一约束保持“商户 + 文章 + 平台”。任何已创建任务永久占用该组合；文章编辑只创建内容版本，不重置去重，也不会自动产生替代任务。原任务符合续发条件时仍走原任务续发；需要发布不同内容时，商户应手动新建一篇独立文章。
- 这样严格落实“同一篇文章只发一次”，避免用户反复编辑版本绕过去重或在提交结果未知时造成二次发布。文章页和发布任务页必须明确展示该规则，不能提示“修改原文后新建任务”。
- 后续如明确需要“提交前失败、修订后允许替代发布”，可评估新增 `supersedesTaskId` 的替代任务机制；该能力需要独立的唯一索引迁移、审计链和真实平台回归，不进入 V1。
